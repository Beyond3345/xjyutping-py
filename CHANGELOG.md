# Changelog

All notable changes to xjyutping, the Python package, are recorded here. The
format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
and versions follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).

This package is the Python port of the LaTeX package
[xjyutping](https://github.com/Beyond3345/xjyutping-tex), which has its own
version numbers and its own changelog. That changelog also holds the full
history of how both packages were built, including the review rounds whose
results this package inherits through the shared data. This file has the
Python releases and the handover notes for the Python side.

The version is written in three places: `version` in `pyproject.toml`,
`__version__` in `src/xjyutping/__init__.py` (`test_version` checks that the
two agree), and `README.md`. A release bumps all three and gets an entry in
Part I.

## [1.0.0] - 2026-09-28

### Added

- **First release** of the Python package `xjyutping`: the Python port of
  the LaTeX package, with the API of
  [xpinyin](https://github.com/lxneng/xpinyin). Python 3.8 or later, no
  dependencies. Class `Jyutping(data_dir=None)`:
  - `get_jyutping(chars, splitter='-', tone_marks='numbers', convert='lower')`
  - `get_jyutpings(chars, splitter, tone_marks, convert, n=10)`: the reading
    in context first, then the other readings.
  - `annotate(text, tone_marks)`: one `(char, reading or None)` pair per
    input character.
  - `segment(text)`: `Segment(text, readings, type)` with the types w/u/m/s
    of the TeX debug log.
  - `set_jyutping(text, reading)`, the equivalent of `\setjyutping`.
  - `get_initial(char, full=False)` and `get_initials(chars, splitter, full)`.
  - The static methods `decode_jyutping` and `convert_jyutping`.
- **Tone styles:** `'numbers'` (default), `None`, `'fancy'` and `'discord'`.
  The last two use the exact code points of Visual Jyutping's web and
  Discord tone maps: ˉ¹ ˊ² ˗₃ ˎ₄ ˏ₅ ˍ₆ and ˉ¹ ⸍² -₃ ⸜₄ ⸝₅ ˍ₆.
- **Same readings as xjyutping-tex 1.1.0.** It uses the same data
  (`src/xjyutping/data/*.tsv`, generated by that package's
  `tools/build-data.py`) and the same run splitting, segmentation, variant
  folding, run-final readings and user overrides.
- **Tests:** 38 pytest tests, including a parity test against a frozen TeX
  debug log (`tests/parity.tex`, `parity_corpus.txt`,
  `parity_expected.txt`). There are 109 runs in the log and no mismatches.
- MIT licence for the code; the data carried CC BY 4.0 (LSHK,
  rime-cantonese) and Apache-2.0 (OpenCC).

# Part II: Handover notes

## 0. Start here

**Where things are:**

| Path | What it is |
| --- | --- |
| `src/xjyutping/__init__.py` | The whole package: `Jyutping`, `Segment`, `TONE_MARKS`. |
| `src/xjyutping/data/*.tsv` | Generated data (see below); never edit by hand. |
| `tests/test_xjyutping.py` | pytest suite (39 tests). |
| `tests/parity_corpus.txt`, `parity_expected.txt`, `parity.tex` | The parity test with the LaTeX package: the corpus, the frozen TeX debug log, and the document that regenerates the log. |
| `pyproject.toml`, `MANIFEST.in` | Packaging (setuptools; the TSV files are package data; the sdist includes the parity files). |
| `README.md`, `LICENSE`, `CHANGELOG.md` | Documentation, licences (code MIT, data CC BY-SA 4.0), this file. |

**The data** is generated, together with the LaTeX package's `.def` files,
by `tools/build-data.py` in
[xjyutping-tex](https://github.com/Beyond3345/xjyutping-tex). It writes here
when this repository sits next to xjyutping-tex (or with
`--py-data DIR`). The files are:

- `chars.tsv`: character, default reading, other readings, polyphone flag;
- `finals.tsv`: reading at the end of a run;
- `variants.tsv`: variant, canonical character;
- `words.tsv`: word, readings.

The sources and every rule for choosing readings are described in that
repository's README and changelog.

**Invariants to keep:**

1. **The same readings as the LaTeX package.**
   `test_parity_with_tex_package` compares every segment, reading and type of
   `tests/parity_corpus.txt` with the LaTeX package's debug log.
   - When the data or the segmentation changes on purpose, regenerate
     `parity_expected.txt`: compile `tests/parity.tex` with
     `TEXINPUTS=<xjyutping-tex>: LUAINPUTS=<xjyutping-tex>:` and
     `max_print_line=10000`, then copy the `xjyutping>` lines. Check the diff
     by hand.
2. **Reading fixes belong in xjyutping-tex's `tools/build-data.py`**, never
   in the TSV files or the code.
3. **The algorithm mirrors the TeX package** (section 2). A change on one
   side needs the same change on the other.
4. **Python 3.8 compatibility:** no `match`, no `X | Y` unions evaluated at
   runtime, no 3.9+ string methods.
5. **Versioning** follows SemVer:
   - MAJOR: an incompatible change of the API (a method, argument or return
     value);
   - MINOR: a backward-compatible feature, or new vocabulary (1.1.0);
   - PATCH: bug fixes and reading corrections.

**How to test:**

```bash
python3 -m pip install --upgrade pip && pip install -e '.[test]' && pytest tests
```

Without installing, run `PYTHONPATH=src python3 -m pytest tests`. All tests
must pass, including `test_parity_with_tex_package`. To check a release,
build the sdist and wheel and run the tests from the extracted sdist.

## 1. How the port was built (with xjyutping-tex 1.1.0)

The port was written by an agent against a frozen copy of the LaTeX package
1.0.0. It took xpinyin's API and reproduced the LaTeX package's algorithm:
runs, segmentation by dynamic programming, word and character lookup, and
user settings. The parity with TeX was then checked on a 668-character
corpus: 0 mismatches.

Three independent reviewers then checked it, each from one angle:

- reading parity with TeX, on a new 1 021-character corpus: 119 runs
  compared line for line;
- API, packaging and docs: the README examples run as doctests; wheel and
  sdist contents;
- edge cases and tone styles.

Every finding was reproduced before it was fixed. The author's own 35 tests
had passed.

- **P-1. CR line ends** (reported by all three reviewers). A lone CR was not
  counted as a line end, so `'\r\r'`, a blank line to TeX, did not end a
  run. That changed segmentation and the run-final 呢.
  - Fix: `_runs` counts `\n`, and `\r` not followed by `\n`.
  - Test: `test_runs_cr_line_ends`, with expected values from a TeX log.
- **P-2. The sdist lacked the parity files,** so its own test suite failed
  (2 tests, FileNotFoundError). Fix: `MANIFEST.in` includes `tests/*.txt`
  and `*.tex`.
- **P-3. The README's editable install failed** with pip 21.2.4, since
  editable installs need pip 21.3 or later. The README now upgrades pip
  first.
- **P-4. `license = {text = "MIT"}` in `pyproject.toml`** triggered a
  setuptools deprecation that becomes a build error after 2027-02-18.
  Removed; `License-File` and the classifier remain.
- **P-5. The README's run-final example showed a word-list entry** instead
  of the run-final rule. It was replaced with 呢張床好平，好麻煩呢？
- **P-6. `set_jyutping` on a character missing from the data did nothing.**
  TeX reads such a character without context and with type `u`. It is now
  its own run of type `u`; test `test_set_jyutping_char_not_in_data`.
- **P-7. `set_jyutping` rejected whitespace** that `\setjyutping` ignores.
  It now strips spaces, tabs, CR and LF; test
  `test_set_jyutping_ignores_spaces`.

Timing on the development Mac (Python 3.9):

- `Jyutping()` takes about 0.08 s;
- `annotate` on 10 000 characters takes about 0.02 s.

## 2. How the port maps to the LaTeX package

| TeX (`xjyutping.sty`) | Python (`src/xjyutping/__init__.py`) |
| --- | --- |
| a character is Chinese iff `\xjp@c@<char>` exists | `c in self._chars` |
| runs: spaces and single line breaks between characters continue a run; `\par`/blank line ends it | `_runs` (ASCII space, tab, CR, LF; two line ends end the run; U+3000 ends it) |
| `\__xjyutping_flush:` (DP, 100000 per segment + 1 per single, `<=` so longer final word wins; bound `\xjp@e@` raw or canonical) | `_segment_run` (same costs and comparison; bound `_longest`, computed from `words.tsv` at load) |
| `\__xjyutping_emit:nn` word: raw key, else canonical; type `u` if `\xjp@uw@` | same, `self._user_words` |
| `\__xjyutping_lookup:nn` single: user, then `\xjp@f@` at run end, then default; type m/s from `\xjp@m@` | same (`_user_chars`, `_finals`, polyphone flag in `chars.tsv`) |
| `\__xjyutping_set:nnn` / `\__xjyutping_set_word:nn` | `set_jyutping` (raw and canonical keys, longest bound) |
| `debug` log `銀ngan4:w…` | `segment()` |

Differences by design:

- Python has no markup, so it has nothing like the command table, footnote
  runs, `\xjyutping` manual readings or plain mode. The parity corpus
  therefore has TeX's commands resolved into the runs TeX makes of them.
- `chars.tsv` lists the other readings of every character (for
  `get_jyutpings`), not only of flagged polyphones.
- `Segment` has no field for the other readings. The parity test reads them
  from `_chars`; users get them through `get_jyutpings`.
- `get_jyutping` drops whitespace between Chinese characters, U+3000
  included, although U+3000 ends a run for segmentation.

## 3. Version 1.1.0

Data only, plus documentation.

- The data of xjyutping-tex 1.2.0 was copied in by its build: 640 more
  characters, 2 291 more words and the two hand fixes.
- The parity file was regenerated with both TeX engines, which agree.
- `test_added_vocabulary` was added. The README examples still run
  unchanged (24 doctests). `python -m doctest README.md` counts the closing
  code fence as expected output, so strip the fences first:

  ```bash
  PYTHONPATH=src python3 -c "import doctest,re; t=re.sub(r'(?m)^\x60{3}.*$','',open('README.md',encoding='utf8').read()); r=doctest.DocTestRunner(optionflags=doctest.NORMALIZE_WHITESPACE); r.run(doctest.DocTestParser().get_doctest(t,{},'README','README.md',0)); print(r.summarize())"
  ```
- The code did not change.
- **Release to PyPI** (the name `xjyutping` was free on 2026-09-28):

  ```bash
  python3 -m pip install --upgrade build twine
  python3 -m build
  python3 -m twine check dist/*
  python3 -m twine upload dist/*
  ```

  The 1.1.0 wheel and sdist were built this way and checked: `twine check`
  passes, the wheel installs into a clean virtual environment, and the 39
  tests pass from the extracted sdist. `twine upload` asks for a PyPI API
  token (user name `__token__`); upload to TestPyPI first with
  `--repository testpypi` if in doubt.
